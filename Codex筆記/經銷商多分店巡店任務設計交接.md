# 經銷商多分店巡店任務設計交接

更新日期：2026-09-04  
狀態：待移至另一台開發機，配合實際專案程式碼繼續確認與設計

## 一、問題背景

目前庫存、每日實銷及陳列資料的來源只提供 `DealerCode`，沒有分店代碼。因此，當同一個經銷商有多家實體分店時，系統無法判斷某筆庫存或實銷屬於哪一家分店。

這在目前業務情境中可以接受：

- 庫存、實銷及陳列回傳仍以經銷商 `DealerCode` 為資料單位。
- 同一 DealerCode 下的多家分店可以共用同一份經銷商彙總庫存。
- 真正需要區分分店的是巡店任務，因為不同分店可能由不同業務負責。
- 有多分店需求的經銷商只占約 1%～2%，不希望為少數例外大幅修改既有資料結構。

## 二、目前建議方案

優先採用「例外派工設定」，暫時不建立完整的經銷商分店主檔，也不修改庫存、實銷、陳列及經銷商權限的資料模型。

基本原則：

- 庫存、實銷、陳列回傳：繼續使用原本的 `DealerCode`。
- 經銷商登入及資料權限：繼續使用原本的 `DealerCode`。
- 分店只代表巡店地點及負責業務，不代表庫存所有權。
- 產生巡店任務時，只有列入例外設定的 DealerCode 才展開為多張分店任務。
- 一般經銷商維持原流程，不受影響。

## 三、例外設定範例

初期可以使用 JSON 或現有的系統設定機制保存多分店資料，不一定要立刻製作後台管理頁。

```json
{
  "D001": [
    {
      "branchKey": "D001-TAIPEI",
      "branchName": "台北店",
      "address": "台北市……",
      "salesUserId": "S001"
    },
    {
      "branchKey": "D001-TAICHUNG",
      "branchName": "台中店",
      "address": "台中市……",
      "salesUserId": "S008"
    }
  ]
}
```

巡店任務產生邏輯：

```text
一般 DealerCode
→ 依既有流程產生一張任務

有例外設定的 DealerCode
→ 依設定展開為多張分店任務
→ 每張任務寫入對應的業務、分店名稱及巡店地址
```

庫存查詢仍只使用原始 DealerCode：

```text
DealerCode = D001
```

因此台北店及台中店的負責業務可以看到同一份 D001 彙總庫存，但各自只處理自己的巡店任務。

## 四、完全不修改資料庫的成立條件

現有巡店任務資料表必須已經能保存任務建立當下的以下資料：

- 負責業務 ID
- 店名或任務顯示名稱
- 巡店地址
- 可唯一識別每一張任務的任務編號

如果上述資料已經直接保存在任務記錄中，就可以只修改程式及設定檔，不修改資料庫。`branchKey` 可用於產生任務編號，例如：

```text
D001-TAIPEI-202609
D001-TAICHUNG-202609
```

## 五、無法完全不修改資料庫的情況

如果巡店任務表目前只保存 `DealerCode`，而負責業務、店名及地址每次都是從 Dealer 主檔即時查詢，兩張相同 DealerCode 的任務在資料上便沒有可靠方式區分分店。

遇到這種情況，建議的最小修改不是建立完整的 `DealerBranch` 主檔，而是只在巡店任務表增加必要的任務快照欄位，例如：

- `BranchKey`
- `BranchName`
- `VisitAddress`
- `AssignedSalesUserID`（如果現有任務尚未保存）

只增加實際缺少的欄位，不需要全部新增。

## 六、不建議的處理方式

不建議直接把分店資訊塞進正式 DealerCode，例如將 `D001` 拆成 `D001-A`、`D001-B`。

這種方式可能連帶影響：

- 庫存匯入及資料配對
- 實銷與陳列回傳
- 經銷商登入權限
- 報表統計
- DealerCode 唯一性及既有資料關聯

修改範圍和風險可能比新增一個最小任務欄位更大。

也不建議只把分店資訊寫在一般備註欄後再解析。備註不是穩定的識別鍵，後續查詢、報表及維護都容易出錯。

## 七、初步修改範圍估算

在巡店任務已保存業務、名稱及地址的前提下：

| 區域 | 預計是否修改 | 說明 |
|---|---:|---|
| 資料庫結構 | 否 | 不新增完整分店主檔 |
| 庫存匯入 | 否 | 繼續只認 DealerCode |
| 實銷／陳列回傳 | 否 | 維持經銷商層級 |
| 經銷商權限 | 否 | 維持原 DealerCode 權限 |
| 多分店例外設定 | 是 | 新增 JSON 或沿用既有設定機制 |
| 巡店任務產生 | 是 | 特殊 DealerCode 展開成多張任務 |
| 業務任務查詢 | 可能 | 確認是依任務上的業務 ID 過濾 |
| 巡店任務畫面 | 小幅修改 | 顯示分店名稱和對應地址 |
| 報表 | 可能 | 確認需要顯示 Dealer 名稱或分店名稱 |
| 後台管理頁 | 初期可不做 | 先以設定檔維護少數例外 |

粗略估計：

- 約修改 3～6 個程式位置。
- 約 100～250 行程式碼，實際仍視現有架構而定。
- 開發及基本測試約 1～3 個工作天。
- 若任務表缺少必要欄位，需再增加一次小型資料庫 migration 及相應測試。

以上只是結構性估算，必須在開發機讀取實際專案後才能確認。

## 八、到另一台開發機後的優先檢查項目

1. 找出 Dealer 主檔、巡店任務表及業務人員表的實際名稱與欄位。
2. 確認巡店任務是建立時保存業務 ID，還是查詢時由 Dealer 主檔推導。
3. 確認巡店任務是否保存店名和地址快照。
4. 找出批次或 API 產生巡店任務的程式入口。
5. 確認業務端任務清單依什麼欄位做權限過濾。
6. 確認任務完成、照片上傳、簽到及陳列回傳是依 Task ID，還是只依 DealerCode。
7. 確認報表是否將 DealerCode 當成唯一的一次巡店；多張分店任務可能需要調整計數方式。
8. 檢查任務唯一鍵是否允許同一 DealerCode、同一日期存在多張任務。
9. 檢查刪除、重建或重新排程任務時，是否可能把同 DealerCode 的其他分店任務一併處理。
10. 完成上述確認後，再決定能否維持零資料庫修改，或只增加最小任務快照欄位。

## 九、建議測試情境

- 一般單店 DealerCode 仍只產生一張巡店任務。
- 多分店 DealerCode 能產生多張任務，而且分派給不同業務。
- 不同業務只看到自己負責的分店任務。
- 多家分店查到的是同一份 DealerCode 彙總庫存，資料沒有被複製或加倍。
- 任一分店完成巡店，不會把同 DealerCode 的其他分店任務一起標示完成。
- 分店任務的照片、簽到、備註及狀態都依 Task ID 分開保存。
- 原有經銷商登入、實銷及陳列回傳流程不受影響。
- 報表可以正確區分「經銷商數」與「巡店任務／分店數」。

## 十、目前暫定結論

因多分店只占約 1%～2%，目前最合適的方向是：

> 維持 DealerCode 作為庫存、實銷、陳列及經銷商權限的共同單位；以少量例外設定把巡店任務展開成不同地點並分派給不同業務。

先不要建立完整的分店主檔。只有在實際程式確認巡店任務無法保存分店快照，或未來多分店比例及管理需求明顯增加時，再考慮最小欄位修改或正式導入分店資料模型。
